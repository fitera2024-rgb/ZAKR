# Универсальный сервис корректирующих переносов по выбранным счетам и иерархии организаций

**Версия контракта:** `HAT-TRANSFER-CONTRACT-v1`  
**Дата:** 27.08.2026  
**Статус:** проект для реализации Codex  
**Заменяет частный контракт:** `UK26-TRANSFER-CONTRACT-v1`  
**Рабочее имя сервиса:** `Hierarchy Account Transfer` (`HAT`)

---

## 0. Критически важное правило направления проводки

Направление корректирующей проводки нельзя определять:

- по названию организации;
- по предположению «из юридического лица в управленческую организацию»;
- по префиксу подразделения;
- по заранее зафиксированной стрелке `source → target`;
- по одному только дебетовому либо кредитовому файлу.

Для каждого выбранного счета `A` сервис обязан рассчитать по каждой точной аналитике:

```text
net(A, analytics) = debit_turnover(A, analytics) - credit_turnover(A, analytics)
```

В типовой ошибке:

- на аналитике `S` остался положительный дебетовый остаток: `net(S) > 0`;
- на связанной аналитике `T` имеется избыточный кредитовый оборот: `net(T) < 0`.

Балансирующая запись всегда определяется математически:

```text
Дт A — аналитика T, где имеется недостаточный дебет / избыточный кредит;
Кт A — аналитика S, где остался необнуленный дебет.
```

Сумма полной корректировки:

```text
amount = net(S)
```

при обязательном условии:

```text
abs(net(S) + net(T)) <= tolerance
```

После моделирования:

```text
source_after = net(S) - amount
target_after = net(T) + amount
```

обязательно должны выполняться все условия:

```text
abs(source_after) <= tolerance
abs(target_after) <= tolerance
abs(source_after) < abs(net(S))
abs(target_after) < abs(net(T))
```

Любая запись, которая не уменьшает абсолютный остаток одновременно на обеих аналитиках, блокируется как:

```text
BLOCKED_DIRECTION_WOULD_WORSEN_BALANCE
```

В сервисе не должно быть «тихого», административного или debug-режима, позволяющего выгрузить ухудшающую проводку.

# Часть I. Функциональный и технический контракт

## 1. Назначение

Сервис принимает полный журнал проводок за выбранный период, иерархию организаций и подразделений и список счетов, выбранных пользователем.

Пользователь выбирает один корневой узел из списка верхних уровней иерархии. Сервис включает в область анализа:

- сам выбранный верхний узел;
- всех прямых потомков;
- всех потомков любого уровня вложенности;
- только строки журнала, относящиеся к этому дереву.

Для каждого выбранного счета сервис:

1. анализирует дебетовые и кредитовые обороты;
2. выявляет аналитику, где расход или иной дебетовый оборот накоплен, но не списан;
3. выявляет связанную аналитику, где кредитовое списание проведено без достаточного дебетового оборота;
4. доказывает соответствие организаций, подразделений и прочих аналитик;
5. моделирует корректировку;
6. формирует проводку `Дт выбранного счета / Кт того же счета` только после прохождения всех проверок;
7. создает контрольный отчет и файлы загрузки по ключу `Дата + Организация документа`.

Частный сценарий счета 26 и верхнего уровня «9 Управляющая компания» остается обязательным регрессионным примером, но не должен быть зашит в код.

## 2. Границы версии v1

### 2.1. Поддерживается

- один выбранный корневой узел иерархии на один запуск;
- произвольный непустой список точных счетов;
- любое количество дочерних организаций и подразделений внутри выбранного дерева;
- перенос внутри одной организации между подразделениями;
- перенос между разными организациями внутри одного выбранного дерева — только при доказанной связи и поддерживаемом способе экспорта;
- несколько месяцев во входном диапазоне, но расчеты и сопоставления выполняются раздельно по каждому месяцу;
- несколько сценариев во входном файле, но один явно выбранный сценарий на запуск;
- точное сопоставление аналитик;
- детерминированные правила соответствия организаций и подразделений;
- контрольный отчет при любом результате, включая полностью заблокированный запуск.

### 2.2. Не поддерживается автоматически

- перенос между разными верхними уровнями иерархии;
- сворачивание разных счетов между собой;
- автоматическое включение субсчетов по строковому префиксу;
- fuzzy/Levenshtein-сопоставление;
- частичное закрытие несовпадающих сумм;
- ручное изменение направления после расчета;
- перенос в корреспондирующий счет 90, 91, 79 или любой другой счет;
- исправление статьи, направления деятельности или субконто без отдельного подтвержденного правила;
- автоматическая выгрузка, если способ кодирования организаций в шаблоне 1С не доказан.

## 3. Термины

### 3.1. Корневой узел (`root organization`)

Выбранный пользователем верхний уровень иерархии. Идентифицируется стабильным кодом, а не только отображаемым наименованием.

### 3.2. Область анализа (`scope`)

Корневой узел и все его потомки любого уровня вложенности.

### 3.3. Выбранный счет (`selected account`)

Точное нормализованное значение счета, явно включенное пользователем в запуск, например:

```text
25
26
44.1
44.2
```

Счет `26` не включает автоматически `26.01`, а счет `44` не включает автоматически `44.1`, если это не подтверждено отдельным справочником плана счетов или явным списком.

### 3.4. Балансовая корзина (`BalanceBucket`)

Точный набор оборотов одного выбранного счета по одной стороне аналитики:

```text
период + сценарий + валюта + счет + организация + подразделение
+ направление деятельности + субконто 1..4
```

### 3.5. Исходная аналитика `S`

Аналитика выбранного счета, на которой после учета всех дебетовых и кредитовых строк остается положительный дебетовый остаток.

### 3.6. Целевая аналитика `T`

Связанная аналитика того же счета, на которой имеется отрицательный остаток из-за кредитового оборота, не обеспеченного достаточным дебетом.

Термины `source` и `target` описывают расчетное состояние, а не юридический статус организации.

## 4. Пользовательский сценарий

1. Пользователь загружает журнал проводок.
2. Пользователь загружает иерархию организаций и подразделений.
3. Пользователь при необходимости загружает шаблон выгрузки 1С.
4. Сервис выполняет предварительный осмотр файлов и показывает:
   - доступные периоды;
   - доступные сценарии;
   - верхние уровни иерархии;
   - счета, найденные в журнале;
   - количество строк по каждому счету и каждой стороне.
5. Пользователь выбирает:
   - один верхний уровень иерархии;
   - один сценарий;
   - период или диапазон месяцев;
   - один или несколько счетов;
   - дату документа либо политику даты;
   - профиль правил сопоставления.
6. Сервис показывает предварительный состав области анализа и обнаруженные/неподтвержденные пары.
7. Пользователь запускает анализ.
8. Сервис создает контрольный отчет.
9. Экспорт разрешается только для строк `READY` и только после повторной проверки инвариантов.

## 5. Что сервис делает

1. Загружает полный журнал проводок за выбранный период.
2. Загружает и валидирует иерархию.
3. Строит дерево и вычисляет полный набор потомков выбранного корневого узла.
4. Отсекает строки вне выбранного дерева до финансового сопоставления.
5. Нормализует строки, счета, коды, даты и суммы без потери оригинальных значений.
6. Разворачивает каждую строку журнала в ноль, одно или два события выбранных счетов:
   - событие дебетовой стороны, если `Счет Дт` выбран;
   - событие кредитовой стороны, если `Счет Кт` выбран.
7. Проверяет принадлежность подразделения организации на соответствующей стороне счета.
8. Считает отдельно дебетовый и кредитовый оборот по каждой точной аналитике.
9. Строит положительные и отрицательные остатки для каждого счета отдельно.
10. Строит только подтвержденные пары организаций и подразделений.
11. Ищет единственную точную пару `S ↔ T` внутри выбранного дерева.
12. Проверяет одинаковый счет, период, сценарий, валюту и обязательные аналитики.
13. Проверяет совпадение суммы в пределах допуска.
14. Формирует математически безопасное направление `Дт A T / Кт A S`.
15. Моделирует состояние до/после.
16. Проверяет возможность представить организации в целевом шаблоне.
17. Формирует детерминированный `correction_id`.
18. Исключает уже примененные корректировки.
19. Создает контрольный отчет независимо от наличия готовых проводок.
20. Создает файлы загрузки только по доказанным корректировкам.

## 6. Что сервис не делает

Сервис не должен:

- анализировать счет, который пользователь не выбрал;
- использовать строки за пределами выбранного дерева для подбора суммы;
- смешивать разные верхние уровни иерархии;
- смешивать разные счета, периоды, сценарии или валюты;
- придумывать дебетовый или кредитовый оборот;
- считать наличие кредитового списания по одному только названию документа;
- строить проводку только по равенству сумм;
- строить проводку только по похожести наименований;
- менять счет в процессе исправления;
- менять статью расходов, направление деятельности или субконто;
- использовать `float` для денег;
- автоматически включать субсчета по строковому префиксу;
- экспортировать `BLOCKED`, `REVIEW` или `PROPOSED`;
- загружать реальные учетные файлы в Git или внешние сервисы;
- скрывать исключенные строки и причины блокировки.

## 7. Входные данные

### 7.1. Полный журнал проводок — обязателен

Формат `.xlsx`. Допускается:

- один файл, содержащий обе стороны проводок;
- несколько файлов за разные месяцы;
- отдельные файлы дебетовых и кредитовых событий только при наличии надежного идентификатора строки и общего формата аналитик.

Для финальной выгрузки журнал должен содержать фактические строки обеих сторон. Файл только с `Дт` выбранного счета не является достаточным доказательством корректировки.

Поддерживаемые фактические заголовки:

- `№`
- `Документ`
- `Дата`
- `Организация`
- `Вид операции`
- `Счет Дт`
- `Валюта Дт`
- `Сумма в валюте Дт`
- `ЦФО (подразделение) Дт`
- `Направление деятельности Дт`
- `Субконто Дт`
- `Субконто2 Дт`
- `Субконто3 Дт`
- `Субконто дт4`
- `Счет Кт`
- `Валюта Кт`
- `Сумма в валюте Кт`
- `ЦФО (подразделение) Кт`
- `Направление деятельности Кт`
- `Субконто Кт`
- `Субконто2 Кт`
- `Субконто3 Кт`
- `Субконто кт4`
- `Сумма в валюте учета`
- `Содержание`
- `Сумма в валюте отчетности`
- `Сценарий`
- `Счет дт. (исх)`
- `Счет кт. (исх)`

Минимально обязательные поля:

- дата;
- организация строки;
- счет Дт;
- счет Кт;
- сумма в валюте учета;
- сценарий;
- подразделение и аналитики соответствующей стороны выбранного счета.

Правило стороны:

- если выбранный счет находится в `Счет Дт`, используются поля дебетовой стороны;
- если выбранный счет находится в `Счет Кт`, используются поля кредитовой стороны;
- если один выбранный счет одновременно указан по Дт и Кт, создаются два события одной исходной строки;
- исходная строка всегда сохраняется целиком для аудита.

### 7.2. Иерархия организаций и подразделений — обязательна

Поддерживаемые поля исходного файла:

- `Головная организация`;
- `Верхний уровень иерархии`;
- `ИНН`;
- `Код`;
- `Без перевыставления`;
- поля ЦФО;
- полное юридическое наименование;
- сокращенное юридическое наименование.

Если файл содержит отдельные поля непосредственного родителя, они используются для рекурсивного дерева. Если имеется только поле `Верхний уровень иерархии`, область определяется как:

```text
выбранный верхний уровень
+ все строки, у которых Верхний уровень иерархии равен выбранному узлу
```

Обязательные свойства иерархии:

- стабильный код узла уникален;
- путь узла однозначен;
- циклы отсутствуют;
- один узел не может принадлежать двум корням;
- подразделение имеет одного подтвержденного владельца;
- дубли наименований допускаются только при разных кодах и путях.

Если стабильные коды отсутствуют, анализ может быть выполнен в режиме `REVIEW`, но финансовый экспорт блокируется как `BLOCKED_UNSTABLE_HIERARCHY_IDENTITY`.

### 7.3. Справочник плана счетов — опционален

Нужен только для режима включения субсчетов.

Без справочника:

- выбираются только точные счета;
- строковое правило `account startswith selected_account` запрещено.

При наличии справочника должны использоваться стабильные коды родитель/потомок.

Базовый импортный лист называется `Загрузка_A_AA` и содержит ровно 27 колонок в указанном порядке:

10. `СуммаВВалютеУчета`
11. `СуммаВВалютеОтчетности`
12. `СуммаВВалютеДт`
13. `СуммаВВалютеКт`

- проверку одинакового счета;
- проверку фактического дебета и кредита;
- проверку суммы;
- проверку направления;
- моделирование состояния до/после;
- проверку возможности экспорта организаций.

## 9. Нормализация

Для ключей сравнения:

1. Unicode `NFKC`.
2. Неразрывные пробелы заменить обычными.
3. Убрать пробелы по краям.
4. Повторяющиеся пробелы свернуть до одного.
5. Для сравнения применять `casefold()`.
6. Оригинальный текст всегда сохранять отдельно.
7. Счет хранить строкой, например `26`, а не числом `26.0`.
8. Не удалять точки и иные значимые символы счета.
9. Суммы хранить как `Decimal`.
10. Денежные суммы округлять до копейки через `ROUND_HALF_UP`.
11. Поле `Дата` является авторитетным.
12. Дата из текста документа используется только для предупреждения.
13. Валюты не объединяются.
14. Пустое значение и строка `0` не считаются одинаковой аналитикой.
15. Автоматический fuzzy-match запрещен для `READY`.

Различие даты поля и даты, встроенной в текст документа, получает предупреждение:

```text
DOCUMENT_DATE_TEXT_MISMATCH
```

## 10. Построение области выбранной иерархии

### 10.1. Выбор корня

API предварительного осмотра возвращает только узлы, являющиеся верхними уровнями. Пользователь выбирает один узел по стабильному коду.

### 10.2. Рекурсивное включение потомков

Если известен непосредственный родитель:

```text
scope = root + recursive_descendants(root)
```

Если известен только верхний уровень:

```text
scope = root + all nodes where upper_level == root
```

### 10.3. Изоляция области

Строка журнала может участвовать в расчете только если:

- организация строки входит в `included_organization_codes`;
- подразделение соответствующей стороны входит в `included_department_codes`;
- владелец подразделения также входит в выбранное дерево.

Строки вне области получают `EXCLUDED_OUTSIDE_SELECTED_ROOT` и не могут использоваться даже для закрытия суммы.

### 10.4. Запрет пересечения корней

Если `S` и `T` относятся к разным корневым узлам, кандидат блокируется:

```text
BLOCKED_CROSS_ROOT_PAIR
```

## 11. Выбор счетов

### 11.1. Предварительный список

После загрузки журнала сервис возвращает все найденные нормализованные счета с показателями:

```text
account
debit_row_count
credit_row_count
debit_amount
credit_amount
first_date
last_date
```

### 11.2. Явный выбор

Пользователь выбирает один или несколько счетов. Пустой список запрещен.

### 11.3. Точность выбора

По умолчанию:

```text
selected account == journal account
```

Субсчета включаются только:

- явным перечислением;
- либо по структурному справочнику плана счетов.

### 11.4. Независимость расчетов

Каждый счет обрабатывается отдельно. Запрещено:

- закрывать дебет счета `26` кредитом счета `25`;
- суммировать остатки разных счетов;
- создавать корректировку с разными счетами по Дт и Кт.

## 12. Проверка владельца организации и подразделения

Для каждого `AccountSideEvent` сервис обязан проверить:

- организация строки существует в иерархии;
- подразделение существует в иерархии;
- подразделение принадлежит организации строки либо разрешенному способу организационного кодирования;
- оба узла находятся внутри выбранного корня.

Несоответствие владельца не исправляется автоматически:

```text
BLOCKED_ORG_DEPT_OWNER_MISMATCH
```

Строка с ошибкой владельца остается в листе исходных строк и в блокировках, но исключается из автоматического финансового сопоставления.

## 13. Построение пар организаций и подразделений

### 13.1. Общий принцип

Сервис не предполагает, что одна сторона всегда является юридической организацией, а другая — управленческой. Допустимы:

- одна организация, разные подразделения;
- разные организации внутри одного корня;
- разные уровни вложенности внутри одного дерева.

### 13.2. Допустимые доказательства пары

Пара может получить статус подтвержденной только из одного из источников:

1. `SAME_ORGANIZATION_EXACT` — одна организация и явная пара подразделений.
2. `EXPLICIT_OVERRIDE` — пользовательский файл правил со стабильными кодами.
3. `HIERARCHY_LINK` — отдельное поле иерархии прямо связывает узлы.
4. `STABLE_EQUIVALENCE_CODE` — оба узла имеют один подтвержденный код бизнес-функции.
5. `CONFIGURED_EXACT_TRANSFORM` — для конкретного корня задан детерминированный преобразователь названия и после него имеется точное уникальное совпадение.

Равенство сумм не является доказательством пары.

### 13.3. Запрещенные доказательства

Не допускаются:

- нечеткое совпадение названий;
- совпадение нескольких слов;
- одинаковое окончание названия;
- близость кодов;
- выбор первой найденной строки;
- правило `Б_` без явной конфигурации для выбранного корня;
- автоматическое сопоставление по ИНН при отсутствии связи подразделений.

### 13.4. Уникальность

Для каждой исходной аналитики должна быть не более одной подтвержденной целевой пары в рамках одного точного `match_key`.

Иначе:

```text
BLOCKED_AMBIGUOUS_PAIR
```

### 13.5. Предложения без выгрузки

Сервис может показывать кандидатов на соответствие как `PROPOSED_PAIR`, но они не участвуют в `READY`, пока не подтверждены правилами.

## 15. Расчет оборотов

Для каждой корзины:

```text
debit_turnover = sum(DEBIT events)
credit_turnover = sum(CREDIT events)
net = debit_turnover - credit_turnover
```

Денежные вычисления выполняются только через `Decimal`.

Расчеты разделяются по:

- месяцу;
- сценарию;
- счету;
- валюте;
- полной аналитике.

## 16. Выявление кандидатов

### 16.1. Исходный остаток `S`

```text
source_net > tolerance
```

При этом должно существовать фактическое дебетовое событие выбранного счета.

### 16.2. Целевой остаток `T`

```text
target_net < -tolerance
```

При этом должно существовать фактическое кредитовое событие выбранного счета.

### 16.3. Режим отсутствующего дебета

Для `candidate_mode = MISSING_OR_INSUFFICIENT_DEBIT` допустимы:

- `target_debit_turnover <= tolerance` — дебет отсутствует;
- `target_debit_turnover > tolerance`, но меньше кредита — дебет недостаточен.

Оба случая отражаются отдельным reason code в контрольном отчете.

### 16.4. Обязательное равенство остатка

```text
abs(source_net + target_net) <= tolerance
```

Частичный перенос по `min(source_net, abs(target_net))` в v1 запрещен.

### 16.5. Единственность

Должна существовать ровно одна подтвержденная пара `S ↔ T` по точному ключу.

## 17. Алгоритм сопоставления

Для каждого месяца, выбранного счета и валюты:

1. Построить все `BalanceBucket` внутри выбранного корня.
2. Выделить положительные корзины `S`.
3. Выделить отрицательные корзины `T`.
4. Для каждой `S` найти допустимые `T` только через подтвержденный `PairMapping`.
5. Отфильтровать по точным обязательным аналитикам.
6. Отфильтровать по совпадению суммы.
7. Если кандидатов нет — создать блокировку с конкретной причиной.
8. Если кандидатов больше одного — `BLOCKED_AMBIGUOUS_PAIR`.
9. Если кандидат один — смоделировать проводку.
10. Проверить уменьшение обоих остатков.
11. Проверить дату и способ кодирования организаций.
12. Проверить идемпотентность.
13. Присвоить `READY` только после всех проверок.

Порядок обработки и сортировки должен быть детерминированным.

## 19. Дата корректировки

Поддерживаемые политики:

### 19.1. `EXPLICIT_DATE`

Пользователь задает дату. Она должна находиться в выбранном периоде или иметь явно разрешенный последующий корректировочный период.

Используется дата фактического кредитового события `T`, только если все строки целевой корзины имеют одну дату.

Последний календарный день месяца.

## 20. Организация документа и представимость в 1С

### 20.1. Проблема

Базовый шаблон содержит подразделения по сторонам, но организация документа может быть единой метаданной. Поэтому перенос между разными организациями нельзя экспортировать, пока не доказано, как импортный адаптер кодирует организацию каждой стороны.

### 20.2. Режимы кодирования

#### `DOCUMENT_LEVEL`

Одна организация документа применяется к обеим сторонам. Разрешено только если:

```text
source_organization_code == target_organization_code
```

#### `SIDE_COLUMNS`

Шаблон или адаптер содержит отдельную организацию Дт и Кт. Требуется явное описание колонок и round-trip тест.

#### `DEPARTMENT_OWNER`

Импортный адаптер определяет организацию каждой стороны по владельцу выбранного подразделения. Этот режим разрешается только после локального синтетического приемочного теста адаптера.

#### `VERIFIED_CUSTOM_ADAPTER`

Организация кодируется иным подтвержденным способом. Должен существовать отдельный capability contract и тест.

### 20.3. Блокировка

Если `S` и `T` относятся к разным организациям, а способ представления не доказан:

```text
BLOCKED_CROSS_ORG_EXPORT_NOT_REPRESENTABLE
```

Контрольный отчет формируется, но файл загрузки не создается.

### 20.4. Группировка экспорта

Один файл содержит:

- одну дату документа;
- одну организацию документа;
- одну валютную логику;
- любое количество выбранных счетов, если все строки проходят один и тот же адаптерный контракт.

## 25. Контрольные инварианты

До экспорта обязательно:

1. выбран ровно один корневой узел;
2. список выбранных счетов непустой;
3. все экспортируемые счета входят в выбранный список;
4. обе стороны каждой корректировки имеют один и тот же счет;
5. сумма каждой корректировки строго положительна;
6. сумма дебета всех корректировок равна сумме кредита;
7. все организации и подразделения существуют в иерархии;
8. все узлы входят в выбранный корень;
9. подразделения принадлежат соответствующим организациям;
10. каждая корректировка имеет фактические строки `Дт account` и `Кт account`;
11. период, сценарий и валюта совпадают;
12. обязательные аналитики совпадают точно либо по явно подтвержденному equivalence-rule;
13. `abs(source_net + target_net) <= tolerance`;
14. остатки после корректировки не превышают допуска;
15. абсолютный остаток уменьшается на обеих аналитиках;
16. частичный перенос отсутствует;
17. пара уникальна;
18. отсутствуют дубли `correction_id`;
19. дата документа однозначна;
20. организация документа однозначна;
21. способ кодирования организаций подтвержден;
22. экспортный файл повторно читается и дает те же значения;
23. денежные расчеты нигде не используют `float`;
24. при глобальном блокере и `all_or_nothing_export=true` папка `export` остается пустой.

## 27. Обязательные приемочные тесты

### 27.1. Один счет, одна организация, разные подразделения

Исходно:

```text
A = 26
S: Организация 1 / Подразделение A / Dt=1000 / Kt=0 / net=+1000
T: Организация 1 / Подразделение B / Dt=0 / Kt=1000 / net=-1000
```

Ожидается:

```text
Дт 26 T 1000
Кт 26 S 1000
source_after=0
target_after=0
READY=1
```

### 27.2. Разные организации внутри одного корня

Та же сумма и точная аналитика, подтвержденная пара организаций и подразделений.

Ожидается одна корректировка только при подтвержденном `organization_encoding_mode`.

### 27.3. Разные верхние уровни

`S` и `T` находятся в разных корнях.

Ожидается:

```text
READY=0
BLOCKED_CROSS_ROOT_PAIR
```

### 27.4. Несколько счетов

Выбраны `25`, `26`, `44.1`. Для каждого счета есть отдельная доказанная пара.

Ожидается:

- три независимые корректировки;
- счета не смешиваются;
- один экспортный файл допустим, если совпадают дата и организация документа.

### 27.5. Невыбранный счет

В журнале присутствует ошибка по счету `44.2`, но пользователь выбрал только `26`.

Ожидается:

- по `44.2` не формируется кандидат;
- строки отражаются только в инвентаризации как невыбранные.

### 27.6. Вложенная иерархия

Корень → организация → филиал → подразделение.

Ожидается рекурсивное включение всех уровней.

### 27.7. Отсутствует фактический кредит

Есть только положительный дебетовый остаток.

Ожидается:

```text
READY=0
BLOCKED_NO_CREDIT_TURNOVER
```

### 27.8. Отсутствует фактический дебет

Есть только отрицательный кредитовый остаток без связанной положительной корзины.

Ожидается:

```text
READY=0
BLOCKED_NO_DEBIT_TURNOVER
```

### 27.9. Несовпадение сумм

```text
source_net=1000
target_net=-900
```

Ожидается:

```text
READY=0
BLOCKED_AMOUNT_MISMATCH
```

Частичная проводка на 900 запрещена.

### 27.10. Обратное направление

Попытка сформировать `Дт S / Кт T` должна ухудшить оба остатка.

Ожидается:

```text
BLOCKED_DIRECTION_WOULD_WORSEN_BALANCE
```

### 27.11. Неоднозначная пара

Одна `S` соответствует двум `T` с одинаковой суммой.

Ожидается:

```text
BLOCKED_AMBIGUOUS_PAIR
```

### 27.12. Неустойчивые коды иерархии

В иерархии отсутствуют стабильные коды.

Ожидается контрольный отчет, но финальный экспорт блокируется.

### 27.13. Cross-org не представим шаблоном

Пара доказана, но шаблон имеет только документную организацию и отсутствует capability test.

Ожидается:

```text
BLOCKED_CROSS_ORG_EXPORT_NOT_REPRESENTABLE
```

### 27.14. Идемпотентность

Два запуска на одинаковых входах дают одинаковые ID и порядок.

### 27.15. Уже примененная корректировка

Идентификатор найден в журнале.

Ожидается:

```text
ALREADY_APPLIED
```

### 27.16. Регрессия частного сценария счета 26 / 9 УК

При наличии локальных конфиденциальных файлов старого сценария:

- выбрать корень `9 Управляющая компания`;
- выбрать только счет `26`;
- применить явный профиль соответствий данного корня;
- не добавлять реальные файлы в Git.

Ожидаемые факты для локального файла `26 январьУК.xlsx`, если он доступен:

- 309 строк данных;
- все 309 строк имеют `Счет Дт = 26`;
- все 309 строк имеют сценарий `Факт`;
- общий оборот `17 542 973,65`;
- файл не содержит строк `Кт 26`;
- `READY = 0`;
- присутствует `BLOCKED_NO_CREDIT_TURNOVER`;
- контрольный отчет создан;
- папка финального экспорта пуста.

Это обязательный anti-fabrication тест.
